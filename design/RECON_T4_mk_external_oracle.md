## 1. Item #9 verbatim + rationale

From `constellation-eval-2026-07-06.md:259-262` (section "Missing independent oracles (same-stack
pins → official vectors)"):

> 9. **mk** address rendering is pinned to sibling-toolkit-derived constants (a regression pin, not
>    external validation). Anchor to the **published** BIP-84/86/49 first-address vectors
>    (spec-text mnemonic).

Section rationale (`:202-206`): "The suites are large and, at the codec-math edges, unusually
well-oracled: official BIP-39/84/86/93/341/129 vectors verified byte-identical to upstream this
audit [...] The weaknesses below are the funds-relevant gaps." Item #9 sits under the
"same-stack pins → official vectors" heading — the general class is: a value computed once by a
*sibling* implementation and hardcoded, checked only against *another* run of a closely-related
implementation, never against a value fixed independently by the standard itself.

**Correction to the task's framing.** The prompt's gist ("mk1 xpub decode is checked only against
mk's own round-trip") is not quite item #9's literal text — item #9 is about **address
rendering** (BIP-44/49/84/86 purpose → script-type mapping), not the `xpub_compact.rs` wire-field
decode in isolation. Ground-truthing both (below) shows they are two distinct, complementary gaps
in the same call chain — the SPEC skeleton in §7 covers both, since T4's title ("mk external
oracle") is what the report groups them under and closing address-rendering necessarily touches
the xpub-decode layer underneath it.

## 2. Decode-path locus

`mk1 → Xpub` reconstruction:

- `crates/mk-codec/src/bytecode/decode.rs:43-44` — call site: `decode_xpub_compact(&mut cursor)?`
  then `reconstruct_xpub(&compact, &origin_path)?`.
- `crates/mk-codec/src/bytecode/xpub_compact.rs:43-53` — `XpubCompact::from_xpub`: full `Xpub` →
  73-byte compact form, **dropping `depth` and `child_number`** (reconstructible from
  `origin_path`).
- `crates/mk-codec/src/bytecode/xpub_compact.rs:86-108` — `reconstruct_xpub`: compact form +
  `origin_path` → full `Xpub`. `depth := component_count(origin_path)`; `child_number :=
  last_component(origin_path)` or `Normal{0}` when the path is empty (depth-0/no-path key,
  v0.4.0+).
- `crates/mk-codec/src/bytecode/xpub_compact.rs:119-137` — `decode_xpub_compact`: 73-byte wire →
  `{version[0..4], parent_fingerprint[4..8], chain_code[8..40], public_key[40..73]}`.

Wire fields (standard BIP-32 xpub fields, per the module doc at `xpub_compact.rs:1-15`):
`version` (4 B, mk drops depth/child_number from the wire and reconstructs them from
`origin_path`), `parent_fingerprint` (4 B), `chain_code` (32 B), `public_key` (33 B compressed) —
73 B total (`XPUB_COMPACT_BYTES`).

Downstream, `mk address` (`crates/mk-cli/src/cmd/address.rs:76`) calls `mk_codec::decode(&refs)`
(→ the above path) then derives children via `card.xpub.derive_pub` (rust-bitcoin) and renders via
`derive_support.rs::render_address` (`crates/mk-cli/src/cmd/derive_support.rs:120-138`), which
switches on `AddressType` (inferred from `origin_path`'s hardened purpose at account depth by
`infer_address_type`, `derive_support.rs:94-113`) to call `bitcoin::Address::{p2pkh, p2shwpkh,
p2wpkh, p2tr}`.

## 3. Current-coverage gap

**Layer A — `xpub_compact.rs` field mapping (fully self-referential):**

- `xpub_compact.rs:145-171` `round_trip_full_xpub_depth_4` — builds a `synthetic_xpub` (fixed
  all-`0x42` secret key, fixed dummy fingerprint/chaincode) via `test_helpers::synthetic_xpub`,
  round-trips it through `from_xpub` → `encode_xpub_compact` → `decode_xpub_compact` →
  `reconstruct_xpub`, and asserts equality against the **same in-memory struct it started from**.
  No externally-fixed value anywhere in the assertion chain.
- `xpub_compact.rs:173-188` `reconstruct_depth0_empty_path` — same pattern for the depth-0 case.
- `xpub_compact.rs:190-210` `rejects_invalid_version` / `rejects_truncated_input` — sad-path only.
- `crates/mk-codec/tests/round_trip.rs` and `crates/mk-codec/tests/vectors.rs` (walks
  `src/test_vectors/v0.1.json`) are likewise self-referential: `vectors.rs:1-16`'s own doc says
  the corpus is generated by `gen_mk_vectors` (a bin in this same crate) — "encoder and fixture
  move together," matching the report's item #4 framing verbatim, just for mk instead of md1.

**Layer B — address rendering (cross-tool, shared lineage, not spec-external):**

- `crates/mk-cli/tests/cli_address.rs:1-7` (module doc): "expected addresses are independently
  computed by the toolkit's `mnemonic convert --to address` (cross-tool, not self-referential)."
  This is the exact mechanism item #9 flags. `derive_support.rs:1-8` documents the sibling
  relationship explicitly: "Mirrors the toolkit's `xpub_search/address_search.rs::render_address`
  (re-implemented locally; the sibling rule forbids depending on the toolkit from a codec crate)."
  I.e. mk's address-rendering code was **copy-derived** from the toolkit's, and both call the
  identical `bitcoin::Address::{p2pkh,p2shwpkh,p2wpkh,p2tr}` constructors (verified:
  `mnemonic-toolkit/crates/mnemonic-toolkit/src/cmd/xpub_search/address_search.rs:9-10` imports
  the same `bitcoin::bip32`/`secp256k1` types). A semantic mistake copied into both
  implementations at authoring time (wrong purpose→script-type table entry, wrong HRP selection)
  is invisible to this cross-check, because the "expected" literals
  (`cli_address.rs:25-27`: `V2_84_M0_0_P2WPKH`, `V2_84_M0_0_P2TR`, `V9_44_M0_0_P2PKH`) were
  themselves produced by the sibling implementation, not by the BIP spec text.
  - Nuance for the SPEC author: because these expected values are **frozen string literals**
    (not recomputed inline against the code under test), this layer *does* catch a pure
    `xpub_compact.rs` field-mapping bug in isolation (wrong key material → wrong address ≠ the
    frozen literal). What it does *not* catch is a bug shared by construction between mk and
    toolkit (same wrong builder call, wrong HRP, wrong purpose-table row) or a bug already baked
    into the literal at generation time.

**Adjacent, already-filed FOLLOWUP (same class, different module):**
`design/FOLLOWUPS.md:409-419` — `mk-slip0132-byte-parity-test-self-referential` (open, Low
severity): `slip132_version_bytes_match_slip0132` (`crates/mk-cli/src/slip132.rs:~145`)
self-referentially declares its own 8-entry byte-constant array and round-trips through
`detect_and_normalize` — same "coordinated symmetric edit invisible" shape as Layer A above, one
module over. That entry's option (a) is verbatim the same remedy T4 needs: "pin a published
BIP-49/BIP-84 extended-key test vector (a known real ypub or zpub string from the BIP itself)."
T4's SPEC should either fold this FOLLOWUP in (one shared published-vector fixture covering both
`xpub_compact.rs` and `slip132.rs`) or explicitly cross-reference it and leave it open,
scope-permitting.

## 4. External-oracle options — which is more faithful + feasible

**(a) Published BIP-32/84/86/49 test vectors, encoded to mk1 and decoded back, byte-for-byte.**
Uses the standard's own fixed mnemonic ("abandon abandon ... about," BIP-84/86) and its published
account xpub + first receive/change addresses. Feasible today: `mk-codec` already depends on
`bitcoin` (for `Xpub`), so a test can `Xpub::from_str(<published xpub string>)`, wrap it in a
`KeyCard` at the matching `origin_path` (`m/84'/0'/0'`, `m/86'/0'/0'`), round-trip through
`mk_codec::encode`/`decode`, and assert the decoded `Xpub` equals the parsed one field-for-field —
*and*, layered on top at the `mk-cli` level, feed it through `mk address` and assert the rendered
first receive/change address string matches the BIP's published address literally. This directly
answers item #9's literal ask (anchor address rendering to spec-text vectors) and is genuinely
external: the BIP author fixed these strings before mk or the toolkit existed, independent of
either's source.

**(b) A from-scratch independent xpub base58check decoder in the test (no mk-codec imports).**
xpub serialization is base58check(`version[4] ‖ depth[1] ‖ parent_fingerprint[4] ‖
child_number[4] ‖ chain_code[32] ‖ public_key[33]`) = 78 raw bytes + 4-byte checksum, 111
base58 chars. A ~30-line test-only decoder (base58 alphabet table + double-SHA256 checksum
verify + fixed-offset field slicing) can re-extract `version/depth/parent_fingerprint/
child_number/chain_code/public_key` from a published BIP-32 vector string (e.g. BIP-32 test
vector 1's master xpub, depth 0) **without calling `bitcoin::bip32::Xpub::from_str` or any
mk-codec function**, then assert those independently-extracted fields match what
`XpubCompact::from_xpub`/`reconstruct_xpub` (`xpub_compact.rs:43-53`, `:86-108`) produce when fed
the same key via `Xpub::from_str` (used only as the *input*, not as the verification oracle).
This is the *more faithful* option for Layer A specifically (§3) because it is independent of
rust-bitcoin's own xpub parser too, not just of mk-codec — (a) still ultimately trusts
`bitcoin::bip32::Xpub::from_str` to parse the vector string correctly on the input side, so it
is not a fully independent check of the field-extraction *semantics*, only of the end-to-end
byte identity.

**Recommendation:** do both, layered, matching the report's own two-part framing (address
rendering *and* the decode path underneath it):
1. **(a) first** — directly closes item #9 as filed (cheapest, highest leverage: reuses the
   existing `bitcoin` dependency, no new dev-dependency, and the BIP-84/86 vectors are the most
   widely-cited, easiest to re-verify against source text).
2. **(b) second, scoped narrowly to `xpub_compact.rs`'s 73-byte field mapping** — closes the
   Layer A residual gap named in §3 (a coordinated field-swap surviving both self-round-trip *and*
   the cross-tool address check would require two independently-wrong things to cancel out
   exactly; (b) removes that residual by checking the compact-form fields directly against a
   decoder that shares no code with either mk or rust-bitcoin's xpub parser). Needs a small
   base58check primitive — either a fresh `bs58` dev-dependency (cleanest: zero linkage to
   `bitcoin::base58`) or a ~15-line hand-rolled decoder inline in the test (zero new
   dependencies, matches the project's general preference for in-tree independent reference
   decoders — see the report's item #7 recommendation for md's `parity_smoke`).

**Caveat for the SPEC author (external-protocol-facts rule, CLAUDE.md):** the mnemonic/xpub/address
strings named below are well-known, widely-cited BIP-84/BIP-32 values recalled from training
data — **re-verify every character against the live BIP text
(`bips/bip-0084.mediawiki`, `bips/bip-0086.mediawiki`, `bips/bip-0049.mediawiki`,
`bips/bip-0032.mediawiki`) before pinning them into the SPEC or a test file.** Do not hand-carry
them from this recon doc without a fresh check — this is exactly the "1 valid last word" class of
false-consensus risk the project's research-phase convention exists to guard against. Notes:
- BIP-84's vector uses mnemonic "abandon abandon abandon abandon abandon abandon abandon abandon
  abandon abandon abandon about," account 0, first receive/change addresses under
  `m/84'/0'/0'/{0,1}/0`. High recall-confidence but unverified in this recon pass (no network
  access from this sandbox; verify against the checked-out BIP text or a vendored copy if one
  exists in-repo).
- BIP-86 uses the same mnemonic; published account xpub + first P2TR addresses.
- **BIP-49's vector does NOT use the same mnemonic** — it specifies its own seed directly (not
  BIP-39-derived) on testnet. Do not assume mnemonic reuse across BIP-49 vs 84/86 without
  checking the text.
- BIP-32 test vector 1 (seed `000102030405060708090a0b0c0d0e0f`) publishes a depth-0 master
  xpub — useful for option (b)'s field-decode check since it exercises mk's depth-0/no-path
  reconstruction branch (`xpub_compact.rs:90-97`) against a real (not synthetic) vector.

## 5. RED-under-mutation

Concrete mutation: a **coordinated field-swap** in `XpubCompact::from_xpub`
(`xpub_compact.rs:45-53`, e.g. swapping which struct field receives `xpub.chain_code` vs.
`xpub.public_key`) paired with the mirrored swap in `reconstruct_xpub`'s `Xpub { .. }` literal
(`xpub_compact.rs:100-106`, swapping `chain_code: ChainCode::from(compact.chain_code)` and the
`public_key` line's source field to match). This is the "symmetric-bug class" the report names
generally at `constellation-eval-2026-07-06.md:224-227` (item 3's heading), specialized to mk's
xpub layer.

- **Stays GREEN today** against: `round_trip_full_xpub_depth_4`
  (`xpub_compact.rs:145-171`) and `reconstruct_depth0_empty_path` (`:173-188`) — both compare the
  mutated code's output only to a struct produced by the same mutated code (via `synthetic_xpub`
  → `from_xpub` → decode → `reconstruct_xpub`, no external checkpoint). Also stays green against
  `tests/vectors.rs` (self-generated corpus) and `tests/round_trip.rs` (`synthetic_xpub`-only,
  same pattern).
- **Would likely already RED** against `cli_address.rs`'s `account_84_first_address_matches_toolkit`
  / `account_44_default_p2pkh_matches_toolkit` (frozen literals `V2_84_M0_0_P2WPKH`,
  `V9_44_M0_0_P2PKH`) — because the wrong chain_code/pubkey produces a different rendered address
  than the pinned string. This is the nuance flagged in §3: the *integration*-level cross-tool
  check does catch this specific mutation today, emergently. What proposed T4 option (b) adds is
  a **direct, isolated, unit-level RED** at `xpub_compact.rs` itself (no dependency on the
  address-rendering layer happening to amplify the corruption into a visibly different string),
  plus a genuinely spec-external checkpoint rather than a sibling-implementation one.
- A **pure address-rendering-table** mutation (e.g. swapping the `44`/`49` arms in
  `infer_address_type`, `derive_support.rs:106-111`, or swapping the `p2wpkh`/`p2shwpkh` builder
  calls in `render_address`, `derive_support.rs:129-136`) is the mutation item #9 is actually
  about — **this one is NOT independently RED-proven today** even by `cli_address.rs`, IF (and
  only if) the toolkit's `address_search.rs` carries the identical mistake (shared lineage per
  `derive_support.rs:1-8`'s own doc comment). Confirming whether such a shared-mistake scenario
  is realistic vs. paranoid is exactly what pinning the published BIP-84/86/49 vectors (§4a)
  settles — those are fixed independent of both implementations.
