## T4-a (#9) — address-rendering oracle (closes item #9 as filed)
**Gap (R0 I2 — provenance framing, NOT "uncaught today"):** `cli_address.rs`'s `V2_84_M0_0_P2WPKH`/`V2_84_M0_0_P2TR`/`V9_44_M0_0_P2PKH` literals were **computed by the toolkit's `address_search.rs` (shared lineage)** — they are frozen strings, so a PRESENT-DAY mutation (arm swap / builder swap) DOES RED them (a frozen literal doesn't re-derive at test time). The real gap is **wrong-at-birth**: those literals could have been wrong since generation (a shared-lineage mistake baked into both the toolkit AND mk at authoring time), and the "re-sync drifted literals from the sibling" repair path would propagate a sibling error. A spec-EXTERNAL BIP vector — fixed by the standard before either impl existed — is the only oracle that catches that provenance class.
**Fix (test):** new `crates/mk-cli/tests/cli_address_bip_vectors.rs` (mk-cli is BIN-ONLY — no lib target; drive the `mk` binary via `assert_cmd`, the `cli_address.rs:56-64` idiom — NOT a library render path). **Ingest via the REAL path (R0 I1):** BIP-84 publishes the account key ONLY as a **zpub**, which `bitcoin::bip32::Xpub::from_str` (rust-bitcoin 0.32.8) REJECTS (`UnknownVersion`, `vendor/bitcoin/src/bip32.rs:794-800`). Feed the published account key through **`mk encode --xpub <published key>`** (SLIP-132 zpub→xpub normalization is wired at `cmd/mod.rs:150`, already exercised by `cli_slip132.rs`) at the canonical origin (`m/84'/0'/0'` for the zpub, `m/86'/0'/0'` for the BIP-86 canonical xpub), producing the mk1 card; then `mk address <mk1> --count 2 --chain both`, and assert the rendered receive/change addresses equal the published strings **verbatim** (frozen literals above, NOT re-derived via the toolkit or any m-format binary). Ingesting the real zpub through `mk encode --xpub` also makes T4-c nearly free.
**Named RED mutation:** swap the `84'`↔`49'` arms in `infer_address_type` (`derive_support.rs:106-111`) OR the `p2wpkh`↔`p2shwpkh` builder calls (`render_address`, `:129-136`) OR the `86'`/p2tr arm → the BIP-84 vector renders a non-`bc1q...` (or BIP-86 a non-`bc1p...`) ≠ the published literal → RED. **NOTE (R0 I2):** this mutation ALSO REDs `cli_address.rs`'s existing frozen literals today (they don't re-derive) — expected and fine; T4-a's DISTINCT value is the spec-external provenance anchor (frozen literals could be wrong-at-birth; the BIP vector cannot). Report the RED but do NOT claim "not caught today".
**BIP-49 (optional):** BIP-49's published vector uses its OWN seed on **testnet** (NOT the abandon mnemonic) — including it adds a network dimension. The 84↔49 arm-swap is already RED-proven by the BIP-84 vector (a swap makes 84' render p2sh ≠ `bc1q...`). Include a direct BIP-49 (49', P2SH-P2WPKH) vector only if judged cheap; else file FOLLOWUP `mk-address-bip49-published-vector`.

## T4-b (#9 Layer-A residual) — xpub-decode field oracle
**Gap:** `xpub_compact.rs`'s field mapping (`from_xpub` :43-53 / `reconstruct_xpub` :86-108 / `decode_xpub_compact` :119-137) is tested only self-referentially (`round_trip_full_xpub_depth_4` :145-171, `reconstruct_depth0_empty_path` :173-188 — compares mutated code's output to a struct produced by the same mutated code). A coordinated field-swap (`chain_code`↔`public_key`) survives all self-round-trip tests; it only REDs emergently two layers up via `cli_address.rs` (and only if it amplifies to a visibly different address).
**Fix (test):** new `crates/mk-codec/tests/xpub_compact_external_oracle.rs`. A **from-scratch base58check field-extractor** (a ~15-line inline decoder: base58 alphabet + double-SHA256 checksum verify — mk-codec ALREADY has `sha2`+`hex` dev-deps, so **no `bs58`, no hand-rolled SHA, zero Cargo.lock delta** (M3) — + fixed-offset slicing of `version[4] ‖ depth[1] ‖ parent_fingerprint[4] ‖ child_number[4] ‖ chain_code[32] ‖ public_key[33]`), sharing **zero code** with `mk_codec` OR `bitcoin::bip32::Xpub` on the verification side. Decode the **BIP-32 tv1 master xpub** to independently-extracted fields; separately feed the same key (via `Xpub::from_str`, input side only) through **`XpubCompact::from_xpub(&xpub)`** (public + re-exported, `bytecode/mod.rs:18-31`); **assert the COMPACT-FORM fields byte-for-byte** — `{version, parent_fingerprint, chain_code, public_key}` of the 73-byte compact form (optionally the raw wire slices) — against the independently-extracted fields. **R0 I3 — assert at the compact-form level, NOT the reconstructed `Xpub`:** a *coordinated* `from_xpub`+`reconstruct_xpub` swap cancels (reconstruction becomes identity → a reconstructed-Xpub comparison stays GREEN against exactly the target bug). The depth-0/`child_number=0` no-path branch (`xpub_compact.rs:89-97`) is exercised by the tv1 master (depth 0, parent fp `00000000`).
**Named RED mutation (R0 I3 — must COMPILE + target the compact form):** the `version`↔`parent_fingerprint` source swap in `from_xpub` (`:45-53`) — BOTH `[u8;4]`, so it compiles (unlike `chain_code[32]`↔`public_key[33]`, which is E0308) — REDs the compact-field assertions directly. **Honesty caveat (R0 I2/I3):** the SHA-pinned corpus (`tests/vectors.rs`, `V0_1_SHA256`, byte-exact `encode_bytecode`) + decode's eager version validation (`xpub_compact.rs:126`) already catch most wire-visible variants today; T4-b's DISTINCT value is spec-external provenance + a direct unit-level failure locality, NOT new mutation coverage. Report accordingly.
