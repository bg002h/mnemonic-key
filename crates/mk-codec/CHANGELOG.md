# Changelog — `mk-codec`

All notable changes to the `mk-codec` crate.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and
this crate follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html)
(pre-1.0: a minor bump may break).

**This file starts at 0.5.0.** Earlier releases (0.1.0 … 0.4.2) were tagged
`mk-codec-v*` without a changelog; `git log --oneline mk-codec-v0.4.2` and the
tag list are the record for those.

## [Unreleased]

**SemVer-minor: `encode` refuses cards it used to mint (BIP 32 invalid depth-0 keys, a depth-1 origin fingerprint that is not the parent fingerprint, out-of-range path indices). Wire layout unchanged; decoding unchanged.**

### Added

- `KeyCard::validate`
- `Error::MasterParentFingerprintNonzero`
- `Error::MasterFingerprintMismatch`
- `Error::OriginParentFingerprintMismatch`

### Changed

- **`encode` refuses an origin-path component whose index is 2^31 or more**, in either form, with `Error::InvalidPathComponent` (`component <n> index <i> is out of the BIP 32 range 0..2^31`). Before, it wrote the index with bit 31 set and the card decoded to a different path.
- **`encode` refuses a depth-0 key whose parent fingerprint is not 00000000** with `Error::MasterParentFingerprintNonzero` (BIP 32 test vector 5).
- **`encode` refuses a depth-0 card whose origin fingerprint is not the key's own** with `Error::MasterFingerprintMismatch`. A key with an all-zero chain code may carry 00000000 instead.
- **`encode` refuses a depth-1 card whose origin fingerprint is not the xpub's parent fingerprint** with `Error::OriginParentFingerprintMismatch`.
- `canonical_payload_bytes` keeps accepting a decoded legacy card.
- `GENERATOR_FAMILY` is `mk-codec 0.6`; V19 is regenerated as a valid master; both corpus SHAs are re-pinned.

### Fixed

- **`gen_mk_vectors` (maintainer tool, feature `gen-vectors`) no longer overwrites its own output and reports it as written.** An `--output` named `csid_ext_v0.1.json` is refused before anything is written (exit 64); an `--output` that is the same file as the `csid_ext_v0.1.json` beside it (a hard or symbolic link) now ends with an error and exit 1 instead of exit 0. Both `wrote` lines print only after both files are written and the vectors file reads back as written (bh-mk-I16).

### Compatibility

- Decoders: unaffected. A card minted before 0.6.0 that breaks one of the three
  key-origin rules still decodes, and \`KeyCard::validate\` reports it.
- "`mnemonic-toolkit`: its WIF cards (all-zero chain code, origin fingerprint 00000000) stay valid."

## [0.5.1] — 2026-11-04

### Added

- **`mk_codec::test_vectors::csid_ext`**, with `pub const CSID_EXT_JSON`: the
  `chunk_set_id` extension vector corpus (`csid_ext_v0.1.json`), a file distinct
  from `v0.1.json` (which is byte-unchanged). Purely additive; regenerated by
  `gen_mk_vectors`, with its own pinned SHA-256 in `tests/csid_ext_vectors.rs`.

### Fixed

- **The encoder now refuses an origin path deeper than `MAX_PATH_COMPONENTS`
  with `Error::PathTooDeep`.** Before, `encode_bytecode` wrote the component
  count unchecked and could mint a card that this crate's own decoder refuses.
  The reported count saturates at 255 rather than wrapping.
- **`decode_string` lowercases ASCII only and refuses a non-ASCII data part**
  (mk bug-hunt, `design/FIX_bughunt_mk.md`) with `Error::InvalidChar`, instead of applying Unicode
  lowercasing to the input.
- Doc fix: the `encode()` documentation now says the multi-chunk
  `chunk_set_id` is derived from the payload (as of 0.5.0), not drawn from the
  CSPRNG.

## [0.5.0] — 2026-08-19

### Changed — BREAKING

- **`chunk_set_id` is now DERIVED from the payload, not drawn from entropy.**
  It is the top 20 bits of `SHA-256(canonical_bytecode)`, MSB-first — the hash
  the chunk layer already computes for its cross-chunk integrity suffix, so the
  derivation costs nothing.

  `encode()` previously drew a fresh 20-bit id from the OS CSPRNG on every
  call, so **encoding the same card twice emitted two different cards on the
  wire** (measured 2026-08-14: three `mk encode` runs on identical inputs, three
  different strings).

  SPEC §2.5 already forbade this — it required an encoder to "reuse the same
  value for all subsequent re-encodings of the same card", and a *stateless*
  encoder cannot honour that by drawing entropy per call, having nowhere to keep
  the value chosen at first encoding. **So this is a conformance fix rather than
  a wire-format change:** the format always meant this; the reference
  implementation did not do it.

  Mirrors the sibling format — `md-codec`'s `derive_chunk_set_id` takes the top
  20 bits of its payload hash by the same MSB-first expression.

  **Impact on callers:** a chunked card re-encoded from identical inputs now
  reproduces byte-for-byte. Any fixture, golden vector or transcript that
  recorded a *previous* random `chunk_set_id` will show a different value and
  must be regenerated. Consumers pinning `mk-codec = "0.4"` are unaffected until
  they move the pin.

### Added

- `chunk_set_id` determinism tests (`tests/chunk_set_id_determinism.rs`).
- T4 external oracles: BIP-84/86 addresses and BIP-32 compact-form vectors.
- T2-c `bch_correct ⇒ valid` proptest, mined KATs, and a third fuzz target.
